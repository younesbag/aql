# تسليم تغيير (ship)

الدستور (`CLAUDE.md`) يوجب: لا يُعلَن النجاح قبل بلوغ النشر READY (إن كان لديك نشر Vercel)، ولا يُسلَّم تغيير قبل بوابة البناء. هذه المهارة هي المسار كاملاً. سير العمل: فرع لكل تغيير ثم pull request — لا push مباشر إلى `main`.

> تنبيه: على ويندوز قد يرتدّ cwd الصدفة بعد كل نداء — ابدأ أوامرك بـ`cd` إلى جذر المستودع. تحذيرات CRLF عند الكومِت طبيعية.

## ١. بوابة النطاق

```bash
git status --short
git branch --show-current
```
- أنت على فرع تغييرك (ليس `main`)؟ إن لم تكن: `git switch -c <اسم-يصف-الأثر>`.
- كل ملف في القائمة مقصود؟ إن ظهر ما لا تعرفه — توقّف وافحصه قبل أي إضافة.
- احذف كل المؤقتات قبل المتابعة: `rm -f _smoke-*.mjs _diag-*.mjs`.
- لا ملفات `.env*` ولا مفاتيح ولا ملفات `data/` المعبّأة بمعلومات شخصية ضمن ما سيُضاف.

## ٢. بوابة البناء

```bash
npm run build 2>&1 | grep -E "(Compiled|Failed|error TS|Type error|Error:|✓)" | head -25
npm run lint
```
- النجاح = سطر `✓ Compiled successfully` بلا أخطاء نوع، وlint بلا أخطاء جديدة. أي خطأ → أصلحه أولاً؛ إن تطلّب الإصلاح كسر قرار محسوم (دستور §٢) → صعّد (دستور §٦).
- استثناء وحيد: تغيير يمسّ ملفات md/توثيق فقط — يجوز تخطي البناء.
- تحذير NFT عن تتبّع `data/` معروف وحميد.

## ٣. الإضافة والكومِت

الإضافة بمسارات **صريحة** — لا `git add -A`، والمسارات ذات الأقواس تُقتبس وجوباً:

```bash
git add "app/(app)/content/actions.ts" lib/content/analyze.ts
```

الكومِت عبر heredoc (لا `-m` متعدد الأسطر بأساليب الصدفة المتباينة):

```bash
git commit -m "$(cat <<'EOF'
<عنوان أثرٍ ≤ ٧٢ حرفاً — ماذا تغيّر للمستخدم/النظام>

<المشكلة وسببها الجذري — سطران>
<العلاج ولماذا هذا الشكل — سطران>
- <ملف>: <ما تغيّر فيه>
- <ملف>: <ما تغيّر فيه>

تحقّق حيّ: <الأدلة الرقمية — نتائج smoke، نسب استهلاك، سطر سجل مقتبس>

Co-Authored-By: <سطر النموذج إن كانت بيئة التشغيل تمليه>
EOF
)"
```

قواعد الرسالة:
- العنوان يصف **الأثر** لا الفعل («عرض الأخطاء بالعربية الدقيقة بدل نصّ Next.js العامّ» لا «تعديل actions.ts»).
- إصلاح عطل إنتاج؟ اقتبس سطر السجل الحاسم في الجسم (دستور §٥-و).
- «تحقّق حيّ:» إلزامي متى وُجد تحقق — وإن لم يوجد فاذكر لماذا (توثيق فقط، إلخ).

## ٤. الدفع وفتح الـPR

```bash
git push -u origin HEAD
gh pr create --fill   # أو افتح الـPR من الواجهة؛ الوصف يكرّر «تحقّق حيّ:» ويسمّي ما لم يُتحقَّق منه
```

الدمج بعد المراجعة وفق سياسة المستودع — لا تدمج تغييرك بنفسك دون موافقة المشرفين.

## ٥. التحقق من النشر (إن كان لديك نشر Vercel؛ إلزامي للتغييرات الكودية)

Vercel ينشئ نشر معاينة (preview) لكل PR، ونشر إنتاج عند الدمج إلى `main`.

1. حدّد المشروع: المعرّفات في `.vercel/project.json` المحلي (غير مرفوع إلى git؛ أنشئه بـ`vercel link`). لا تكتب معرّفات مشروعك في ملفات المستودع.
2. اجلب أحدث نشر لفرعك عبر أدوات Vercel (MCP: `list_deployments` ثم `get_deployment`) أو CLI: `vercel ls` / `vercel inspect <url>`.
3. حسب `readyState`:
   - **READY** وحقل commit sha في بيانات النشر يطابق كومِتك → انتقل للتقرير.
   - **BUILDING/QUEUED** → البناء يستغرق ~٣٠–٦٠ ثانية عادة. انتظر قليلاً ثم أعد الاستعلام؛ لا حلقات استعلام محمومة.
   - **ERROR** → اقرأ `errorCode`/`errorMessage` وسجلّ البناء، وطبّق الكتيّب أدناه.
   - READY لكن الـsha قديم → النشر الجديد لم يظهر بعد؛ أعد قائمة النشرات وابحث عن كومِتك.

### كتيّب أعطال النشر

| errorCode / العرض | السبب | الإجراء |
|---|---|---|
| `invalid_max_duration` | `maxDuration` > ٣٠٠ على خطة Hobby | أعده ≤ ٣٠٠ وسلّم تصحيحاً — ولا تعتبر مشكلة المهلة محلولة (التوليد الطويل مكانه طابور العامل) |
| فشل بناء (تجميع/أنواع) | فرق بيئة أو ملف غير مدفوع | اقرأ سجلّ البناء الفعلي — لا تخمّن |
| فشل لسبب خارجي (انقطاع Vercel) | ليس كودك | أبلغ المشرفين بالحالة وأعد المحاولة لاحقاً — لا تعدّل كوداً سليماً |

فشل النشر يعني أن الإنتاج بقي على النشر السابق — الموقع لم ينكسر، لكن تغييرك **غير حيّ**. لا تقرير نجاح.

## ٦. التقرير

موجزاً: hash الكومِت ورابط الـPR + الأثر بجملة + دليل التحقق (نتيجة البناء، حالة النشر READY، أرقام smoke إن وُجدت) + أي قرار اتخذته بنفسك ضمن صلاحياتك + أي اقتراح تحسين (اقتراحاً لا تنفيذاً — دستور قاعدة ٢).
